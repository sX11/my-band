## [Unreleased]

### Added

- **Route map on the workout detail** (`Health/HealthKitManager.swift`, `UI/Workouts/WorkoutsView.swift`, `docs/adr/0009-*.md`): an outdoor workout's detail shows its GPS route on an Apple map, with start and finish markers, read back from the `HKWorkoutRoute` the app saved with it (`route(ofWorkout:)`). Read each time the detail opens and never stored; indoor workouts and workouts without a saved route show no map. ADR 0009 gets an addendum, and the Workouts page footer no longer sends you to the Health app for the route. **Not yet validated on hardware**, including whether band workouts carry a route at all.
- **Edit reminders on the Reminders page** (`UI/Reminders/RemindersView.swift`): swiping a reminder added here to the right opens it in the form, pre-filled (a weekly, monthly or yearly one with its next occurrence, not today), and Save replaces it on the band: delete, then add, through the same paths as Delete and Add; the band's own edit command isn't used, since a daily row can change how many times it has. Save checks the free slots, counting the reminders it replaces, before deleting anything, and re-sends a delete the band didn't take, so an edit never loses the original or leaves it next to the new one. Cancel and a saved edit reset the form. iPhone reminders get Delete only: the next sync would overwrite an edit, so they're edited in the Reminders app. **Not yet validated on hardware.**
- **Reminders on the band** (`BLE/ReminderService.swift`, `UI/Reminders/RemindersView.swift`, `BLE/CalendarSyncService.swift`, `UI/RootView.swift`): a page to the right of Workouts shows the band's reminders, with swipe to delete and a form to add one with a title (up to 20 characters, GadgetBridge's limit), a date and time, and a repeat (once, daily, weekly, monthly, yearly). Daily accepts several times (e.g. 10, 13, 16 and 19): the band holds one time per reminder, so each time becomes a daily reminder with the same title, each taking one slot; Add sends only if they all fit, warns if the band confirms only some of them, and the list shows same-title daily reminders as a single row, which deletes them all together. The section shows how many the band holds when it reports its limit, and Add waits for the band's list. Reminders added here are remembered by title and time, so the iPhone-reminders push never deletes them; that push now goes through the same service, which matches each create ack to the oldest waiting create. Deleting an iPhone reminder here makes the next sync push it back, and a push with an unconfirmed create retries on the next sync. **Not yet validated on hardware**: the band's `maxReminders`, the 20-character limit, and the repeat modes, which follow GadgetBridge.
- **Sleep & trends page** (`UI/Trends/TrendsView.swift`, `Health/HealthTrends.swift`, `Health/HealthKitManager.swift`, `UI/RootView.swift`): swiping right on the Dashboard opens a page with charts of the last 7 days read from Apple Health: sleep per night by stage, resting heart rate, steps, SpO₂ and weight. Trends are Apple Health's totals across every source, so steps include the iPhone's; for sleep, a minute both the iPhone and the band recorded counts once, with the band's stage. Each night belongs to the day it ends on, cut at 18:00. Nothing is stored (ADR 0010). The Health read description in `Info.plist` now names the trends. **Not yet validated on hardware.**
- **Workouts screen** (`UI/Workouts/WorkoutsView.swift`, `Health/HealthKitManager.swift`, `UI/RootView.swift`): swiping left on the Dashboard opens the Workouts page, with the newest 50 workouts My Band wrote to Apple Health, grouped by month, with sport, date, duration, distance, kcal and average HR; a workout opens its times, pace or speed, average METs, average/highest/lowest HR, and indoor or outdoor. Read from Apple Health each time the page appears and never stored; only this app's own workouts, so an iPhone workout never shows as the band's (ADR 0009). Each new workout stores the band's sport in its metadata (`MiBandWorkoutKind`); older ones rebuild it from the activity type, so free training shows as "Workout". The Health read description in `Info.plist` now names the workout list. A locked iPhone refuses the read and the screen asks to unlock. **Not yet validated on hardware.**
- **Live workout on the Dashboard** (`BLE/WorkoutLiveService.swift`, `UI/Dashboard/WorkoutLiveView.swift`, `BLE/BandManager.swift`, `BLE/WorkoutGpsService.swift`): while the band records a workout, a card at the top of the Dashboard shows the sport, elapsed time (pauses excluded), running or paused, live heart rate, steps, kcal and, for GPS sports, distance; tapping it opens a Workout sheet with average pace or speed. The workout comes from `workoutStatusWatch` (8/26); heart rate, steps and kcal from the realtime stream, held from start to finish (`.workout` holder), with steps and kcal counted from the start; distance sums the GPS fixes the app already streams to the band. Nothing is stored; the session ends on finish, when the band is forgotten, or after 10 min without a link (ADR 0008). A Live Activity (`MyBandWidgets` extension) shows the same on the Lock Screen and in the Dynamic Island; iOS starts one only while the app is open, so a workout begun with the phone locked posts a notification and the activity starts when the app is opened. Starting a band workout from the app isn't possible: no known command does it. Card and Live Activity validated on hardware (2026-09-29); **not yet validated** whether live heart rate, steps and kcal flow during a workout, and whether the status timestamp is the workout's start or the event's time.
- **Apple Health sync details** (`Models/HealthSyncLog.swift`, `UI/Dashboard/HealthSyncView.swift`, `Health/HealthKitManager.swift`, `BLE/BandSyncer.swift`): tapping the Apple Health tile opens a sheet with the last sync's samples sent per data type, the band files behind them, and every other type with when it was last sent. HealthKitManager counts each write per type during a sync; the report is kept in UserDefaults. The Dashboard now has three rows of paired tiles: Battery and a smaller Settings tile, Next alarm and Today, Apple Health and Latest metrics. **Not yet validated on hardware.**
- **Latest metrics on the Dashboard** (`Models/LatestMetrics.swift`, `UI/Dashboard/LatestMetricsView.swift`, `UI/Dashboard/DashboardView.swift`, `BLE/BandSyncer.swift`): a Latest metrics tile shows the newest heart rate with SpO₂, stress and resting heart rate, and opens a Health sheet listing the newest value of every reading: the live one-shot, the newest day's summary (stood hours and which hours, resting/average/highest/lowest heart rate, SpO₂, stress), the newest heart-rate, SpO₂, stress and skin-temperature samples, the last night's sleep stages and the scale's last weighing. Each sync overwrites one snapshot in UserDefaults; forgetting the band clears it (ADR 0006). **Not yet validated on hardware.**
- **Today tile on the Dashboard** (`BLE/TodayActivityService.swift`, `UI/Dashboard/DashboardView.swift`, `BLE/BandManager.swift`): beside a now half-width Next alarm tile, a Today tile shows the band's steps, calories, standing hours and a current heart rate. It is a one-shot read of the realtime stats stream (START, stop on the first heart rate above 10 bpm or after 30 s, as GadgetBridge's one-shot does), refreshed every 5 minutes while the app is in front and after a pull-to-refresh sync, and never stored. The stream is shared by named holders, so the Dashboard's reading can't stop a post-workout recovery capture; holders are cleared when the link drops. Supersedes ADR 0001's no-data rule (ADR 0005). **Not yet validated on hardware.**
- **Band settings** (`BLE/BandSettingsService.swift`, `UI/Settings/BandSettingsView.swift`, `UI/Dashboard/DashboardView.swift`): a "Band settings" tile on the Dashboard shows the heart-rate interval and whether all-day SpO₂ and stress are on; tapping it opens a screen for heart-rate monitoring (interval, high/low alerts, sleep monitoring, breathing quality), all-day SpO₂ and its low alert, all-day stress and relax reminder, the stand-up reminder and its hours, goal notifications, and waking the screen on a notification. Ported from GadgetBridge's `XiaomiHealthService` `CMD_CONFIG_*` pairs (type 8) and `XiaomiNotificationService` screen-on (type 7, subtypes 6/7). As with alarms, the band is the source of truth: each edit starts from the band's record, is sent, and that setting is read back. `SpO2` field 2 in `xiaomi.pb.swift` is hand-patched from `bool allDayTracking` to `uint32 mode`, as upstream did: the band uses 0 off / 1 sleep-only / 2 all-day, so sending `true` would have switched on sleep-only. Breathing quality (`breathingScore`) is shown only when the band reports it: the Mi Band 10 acks the set but never stores or returns field 9 (hardware, 2026-09-26). The rest is **not yet validated on hardware**.
- **Last charge date on the Battery tile** (`BLE/BandManager.swift`, `UI/Dashboard/DashboardView.swift`): while not charging, the tile's footer reads "Charged 3 days ago", from `battery.lastCharge.timestampSeconds`. **Not yet validated on hardware** (whether the timestamp marks the start or end of charging).
- **Smart wake-up on band alarms** (`BLE/AlarmService.swift`, `UI/Alarms/AlarmsView.swift`): the New alarm section has a Smart wake-up switch, and a swipe right on an alarm switches it between smart and normal (`AlarmDetails.smart` 1 / 2).
- **Band alarms** (`BLE/AlarmService.swift`, `UI/Alarms/AlarmsView.swift`, `UI/Dashboard/DashboardView.swift`): a "Next alarm" tile on the Dashboard shows the next enabled alarm; tapping it opens the Alarms screen to switch alarms on or off, swipe to delete, and add one with a time and weekdays. The band is the source of truth: each change is sent to it and the list is read back (schedule type 17, subtypes 0/1/2/4, ported from GadgetBridge's `XiaomiScheduleService`; weekday bitmask Mon=1 … Sun=64). The alarm-create reply is routed apart from the reminder reply, so it can't be recorded as a reminder id and deleted by the next calendar sync. Switching an alarm edits the band's own record, so repeat modes the app doesn't model survive; forgetting the band clears the list. Tested on hardware (2026-09-25).
- **Pull to refresh on the Dashboard** (`UI/Dashboard/DashboardView.swift`): pulling down runs the same coalesced sync as the button while the band is connected.

### Changed

- **New app icon** (`My Band/Icon.icon`): a single-stroke lowercase m whose last leg turns into a heartbeat and ends in a pink dot (the heart-rate colour), on the midnight background. Two layers in Icon Composer: the monogram, with glass translucency, and the dot, opaque. The layers are PNG because `actool` ignores `fill="none"` in SVG and fills a stroke, closing the m's counters.
- **User-facing text is in English** (UI, errors, notifications, Siri phrases and `Info.plist` usage strings).
- **First pairing is now treated as a window, not as a connection state** (`BLE/BandManager.swift`, `UI/Setup/ConnectingView.swift`, `UI/ConnectionStatus+UI.swift`): the first connection asks for **two** confirmations, on different screens and in order: the band raises its own dialog, and only then does iOS raise the Bluetooth pairing sheet. Between the two the link **drops** (that is how iOS creates the bond), and the 120 s wait of `.awaitingPairingConfirmation` died with the connection. The wait is now a 180 s *deadline* that survives disconnections and is extended by every packet proving the band is still asking; on reconnecting within the window, `startNonceExchange` restores the patient posture instead of starting over as a routine handshake. The connection screen shows the two steps as a checklist, marks which one is active and counts down the remaining time.
- **`ConnectionState.awaitingPairingConfirmation` no longer names only the band in the UI** (`UI/ConnectionStatus+UI.swift`): the pill says "Confirme o pareamento" ("Confirm pairing") and the specific step ("na pulseira" / "no iPhone", "on the band" / "on the iPhone") comes from `BandManager.pairingStage`, which only moves forward: a late `sub=16` doesn't send the copy back to the band while the iOS sheet is open.
- **The band's battery now comes from the same source as the iOS Batteries widget** (`BLE/BandManager.swift`, `BLE/Services/MiBandUUID.swift`, `Intents/CheckBandBatteryIntent.swift`): besides `FE95`, the connection discovers the standard GATT Battery Service (`0x180F`) and, after auth, reads and subscribes to the Battery Level characteristic (`0x2A19`), the reading iOS shows in the widget. When it exists, it owns `batteryLevel` (Dashboard and shortcut agree with the widget); `CMD_BATTERY` is still requested because only it says whether the band is charging. The intent replaces the blind 3 s `sleep` with `BandManager.refreshBattery`, which actually waits for the replies: the 3 s become a ceiling, not a floor. Without `180F`, everything falls back to the previous path. The read is post-auth only on purpose: touching an encrypted characteristic on an unbonded link would make iOS raise the pairing sheet before the band's dialog (ADR 0003). **To be validated on hardware** whether the Mi Band 10 exposes `180F` to apps: the `Services:` line of the connection log answers it.

### Fixed

- **Outdoor workouts record their GPS route again when the band says "started" before asking for GPS** (`BLE/WorkoutGpsService.swift`): the band can send the workout-started status a few milliseconds before its GPS request, and sends it only once. The GPS request handler reset the started flag, so the app got a fix, told the band GPS was ready, and then forwarded none of the locations; the band stored a GPS file with 0 points and the workout reached Apple Health without a route (hardware log 2026-11-01: a 31-minute walk with a 1 Hz fix stream and no points sent). Only pause, finish and stopping GPS clear the flag now. The started/resumed status is logged at notice level, so its order against the GPS request survives in the device log. **Not yet validated on hardware.**
- **Outdoor workouts no longer start with "weak GPS" on a slow first fix** (`BLE/WorkoutGpsService.swift`): CoreLocation's `locationUnknown` error, which only means no fix yet and that it keeps trying, was answered with the "GPS disabled" reply, so the band reported weak GPS and recorded the workout without a GPS file, leaving it without a route in Apple Health. The app now keeps waiting for the first fix while the band keeps asking, and replies "GPS disabled" only if no fix arrives within 60 s. The first workout-open request of each workout (with the location permission state), the GPS-ready reply with its accuracy, each workout GPS file's point count, and an outdoor workout written without a track are now logged at notice level, so they survive in the device log. **Not yet validated on hardware**: that this is the band's weak-GPS case.
- **iPhone reminders no longer pile up on the band** (`BLE/CalendarSyncService.swift`): the iPhone-reminders push remembered only what it had just created, so a reminder whose delete was lost (a dropped command, a session restart) was forgotten by the next push and stayed on the band for good. A reminder whose next time changes several times a day reached 20 copies. The push now keeps owning every reminder it tried to delete while the band still lists it, and a delete the band didn't take leaves the saved signature unsaved, so the next sync retries it. Once per install, a band reminder titled like an iPhone reminder being pushed is also treated as the push's own (unless it was added on the Reminders page), which clears the copies earlier pushes lost track of; it runs only once because a title alone also matches a reminder the band or another app created. A version prefix on the saved signature makes the first sync after the update run it. **Not yet validated on hardware.**
- **Band weather failing at the top of every hour** (`BLE/WeatherSyncService.swift`): the band asks for weather once per saved location every ~15 min, and with GPS on they all resolve to the same coordinates, so every request repeated the same Open-Meteo call (about 36 an hour) and retried a 429 straight away. In the iPhone log of 2026-10-09 every top of the hour (10:01, 11:01, 12:01) ended in `Weather fetch failed` on HTTP 429. One shared fetch per ~1 km cell is now kept for 10 min; when Open-Meteo fails, the last forecast up to 3 h old answers instead, only while it still covers today, and without counting as a fresh fetch for the proactive-push throttle or for workout weather. A 429 is not retried at once and puts the cell on hold (its `Retry-After`, or 5 min), during which later requests use the cached forecast without a network call.
- **Sleep and cardio recovery with the iPhone locked** (`BLE/BandSyncer.swift`, `Health/HealthKitManager.swift`): the sleep cleanup deletes the app's own samples in the night's window, which a locked iPhone refuses, and that failed the whole sleep write (`Sleep write failed`). With the iPhone locked, sleep is now written without the cleanup and its file stays un-ACKed, like the workout and daily-detail files, so an unlocked sync clears and rewrites the night. Cardio recovery, which reads Health, waits for that same sync instead of logging an error. A locked sync now lifts the 15-min BLE-wake throttle and triggers a sync on unlock (`protectedDataDidBecomeAvailable`); an iPhone that locks mid-sync rewrites sleep without the cleanup instead of failing; the one-time sleep-history repair waits for an unlocked sync; and a file the band sends in place of the one asked for is no longer ACKed at once while locked.
- **Badminton workouts written to Apple Health as "Other"** (`BLE/PacketParser/WorkoutSummaryParser.swift`, `Health/HealthKitManager.swift`, `UI/Dashboard/WorkoutLiveView.swift`, `My BandTests/WorkoutKindTests.swift`): the band records badminton in the free-training layout with `workoutType` 608, which the app did not map, so the workout fell back to free training, written as `.other`. 608 maps to `.badminton`, and every GadgetBridge `XiaomiWorkoutType` code that has a HealthKit activity type gets one (water, racket, team, combat, dance, winter, gym…), several codes per kind (zumba and ballet become dance; futsal and beach soccer, soccer); the ~30 with no HealthKit type (chess, darts…) stay "Other". The same code decides the GPS reply at workout start: court and gym sports answer GPS disabled and are written as indoor; a code that may be outdoor and has no kind of its own (parkour, beach volleyball) stays unmapped, with GPS. Distance for skiing, skating and paddling goes to HealthKit's own types (asks for new permission), and for sailing, surfing, triathlon and the like is not written, instead of inflating walking distance. The live card and Workouts screen show speed for those sports. Dumbbell, barbell, weightlifting and deadlift become functional training, so only code 308 starts strength recording. Workouts already written stay "Other". **Not yet validated on hardware.**
- **Recurring iPhone reminders reached the band as one-shot reminders** (`BLE/CalendarSyncService.swift`, `BLE/Protocol/XiaomiProto.swift`): every reminder went as its next occurrence, so a repeat was missed when no sync ran between two. A plain, open-ended daily, weekly (on one weekday), monthly or yearly rule now goes with the band's own repeat. Rules with an interval, several weekdays or an end still go one occurrence at a time. **Not yet validated on hardware.**
- **The band's alarm limit could be exceeded** (`BLE/AlarmService.swift`, `UI/Alarms/AlarmsView.swift`): Add alarm was only blocked when the band reported `maxAlarms`; without it nothing stopped an 11th alarm. The limit now falls back to 10 (the Mi Band 10's) until the band reports its own, the button waits for the list to be read, and a second tap before the list comes back can't pass the limit. The section shows "N of 10" and, when full, asks to delete one.
- **A sync with the iPhone locked was reported as failed** (`BLE/BandSyncer.swift`, `Health/HealthKitManager.swift`, `Models/HealthSyncLog.swift`, `UI/Dashboard/HealthSyncView.swift`, `UI/Dashboard/DashboardView.swift`): nearly every background sync ended with "Protected health data is inaccessible". Reconciling steps, distance and energy read the iPhone's own totals, and HealthKit refuses reads while the phone is locked; the throw aborted the batch and left the daily-detail files un-ACKed. These three are now written raw per minute (`writeActivity`) with no read at all, and Apple Health merges the minutes the iPhone also recorded by the Data Sources order instead of adding them. Put iPhone above My Band in Health > Steps > Data Sources & Access for the iPhone to win those minutes. Each re-sync replaces the surplus written earlier for the same minute. A sync that fails while processing the band's files now shows its error in the Apple Health sheet. With the phone locked everything is written, but workout and daily-detail files stay un-ACKed until an unlocked sync, since weight, age and cardio recovery depend on Health reads. Workout windows are stored, so a daily-detail file arriving in a later sync than its workout no longer counts the workout's distance and energy twice. **Not yet validated on hardware.**
- **Last sleep in the Health sheet was one fragment of the night** (`UI/Dashboard/LatestMetricsView.swift`): it showed the newest `SleepSession`, but a night arrives as several overlapping sessions. It now merges and de-overlaps them the way the Apple Health write does, and adds awake time.
- **Today tile always said "stood 0 h"** (`BLE/TodayActivityService.swift`, `UI/Dashboard/DashboardView.swift`): the realtime stream's `standingHours` field reads 0 on a Band 10 whose own screen counts stand hours. Stood hours now come from today's daily-summary mask (as of the last sync), and the first realtime event of each reading logs all six raw fields as private values, readable with a private-data logging profile, so the unmapped ones can be identified.
- **"Not authorized" failed every Apple Health sync** (`Health/HealthKitManager.swift`): one data type switched off for the app in Health → Data Access (Steps, on hardware 2026-09-26) makes HealthKit reject the whole `store.save`, so nothing was written. Samples of a type the app can't write are now dropped and named in the log, and workouts and routes are skipped when their type is off. A band file whose samples were dropped this way is left un-ACKed, so the band offers it again and it is written once the type is switched on, rather than deleted unwritten.
- **The band's clock was an hour off in summer time** (`BLE/Protocol/XiaomiProto.swift`): `setCurrentTimeCommand` sent `secondsFromGMT` (which already includes DST) as `zoneOffset` and sent `dstOffset` too, so the band applied DST twice. `zoneOffset` is now the standard offset, as GadgetBridge sends it. Calendar alerts, sent as timestamps, fired an hour off for the same reason.
- **Band reminders fired at the wrong time** (`BLE/CalendarSyncService.swift`, `BLE/BandManager.swift`, `UI/RootView.swift`): date-only reminders went to the band at 00:00 (now 09:00, the iOS default), a reminder's alert was ignored in favour of its due time, overdue reminders filled the 20 slots, and location alerts were treated as times. Each reminder now goes at the next alert the iPhone would give. Before re-creating, the band's list (`CMD_REMINDERS_GET`) is read and only this app's reminders are deleted, by acked id or by title and time, so a missed ack no longer leaves an orphan firing forever. Only create acks (subtype 15) count as ids. Forgetting the band clears the sync state. Calendar events also honour fixed-time alerts.
- **iOS marked the BGTask as failed before the app started** (`BLE/BackgroundSyncManager.swift`): the `expirationHandler` was installed only after the hop to the main actor, and that hop took 6 s in a freshly resumed app (hardware, 2026-09-11): the task expired without a handler and iOS completed it as failed (`Client didn't provide an expiration handler`), which lowers the frequency of later scheduling. The handler is now installed in the `register` closure itself, on the scheduler's queue; on expiry, the app cancels the sync, releases the link and completes the task right away, and `setTaskCompleted` runs exactly once, whether from the sync or from the expiry.
- **A sync opened on a new connection died in the band's session restart** (`BLE/BandSyncer.swift`, `BLE/BandManager.swift`): right after the post-auth init the band reopens the session and swaps keys, and `ensureConnected` resolves on exactly the first auth, so `FETCH_TODAY` went out in the window where the band silently drops commands (or didn't go out at all: without keys, `sendEncryptedCommand` returned silently). The listing blew past its 10 s and took the whole sync with it, sleep included. `BandManager.onSessionRestart` now fails the in-flight exchange at once (`SyncError.sessionRestarted`) and `BandSyncer.surviveSessionRestart` re-sends it after the re-handshake (`BandManager.awaitSession`), for listings and for each file. A command dropped for lack of keys is now logged.
- **A file delivered in place of another was ACKed without being read** (`BLE/BandSyncer.swift`): when the band answered a fetch with another not-yet-confirmed file, the app ACKed it to "unstick" things and moved on, discarding its contents for good. The swapped file arrives complete and with a valid CRC; it is now routed like any other before the ACK. The likeliest candidate to be caught mid-way was the sleep file, the largest in the queue.
- **A failure writing sleep took down the whole batch** (`BLE/BandSyncer.swift`, `Health/HealthKitManager.swift`): the `writeSleep` error escaped `processActivityFiles` and skipped the later writes (manual, workouts, daily detail) and every ACK. Now only the sleep files stay un-ACKed (the band offers them again) and the rest goes on. `deleteExistingSleep` also tolerates `errorNoData`: a window with none of our samples, the first write of a night.
- **`0x03` sleep went to the wrong parser** (`BLE/PacketParser/SleepPacketParser.swift`, `BLE/PacketParser/XiaomiActivityFile.swift`): both sleep subtypes went to `SleepDetailsParser`, but `0x03` has another layout (transition events). Ported GadgetBridge's `SleepStagesParser` (version 2); routing separates `isSleepDetails` (`0x08`) from `isSleepStages` (`0x03` DETAILS). `SleepDetailsParser` also stops guessing offsets for unknown versions (>5): before, arbitrary bytes could pass as HR/SpO₂.
- **Fixed 30 s timeout per file** (`BLE/BandSyncer.swift`): it became an **inactivity** timeout (10 s without a chunk), like GadgetBridge's: a large file still arriving is no longer cut off, and one that never arrives fails sooner.
- **Reconnecting on top of a handshake in progress** (`BLE/BandManager.swift`): `ensureConnected` called during re-authentication (a BGTask at the moment of the session restart) called `connect(to:)`, which puts the state back to `.connecting` and redoes service discovery, with a second `authenticate()`. Now it only waits. Past the `maxBandSessionRestarts` limit, the link is dropped to reconnect cleanly, instead of staying up with every command dropped.
- **Placeholder ids in the listing** (`BLE/BandSyncer.swift`): ids with no timestamp and no version are ignored, as in GadgetBridge: each one only burned a timeout.
- **The battery intent dropped the link before reading the battery, and in the middle of the sync's ACKs** (`Intents/CheckBandBatteryIntent.swift`): it ran `syncNow()` with the default `disconnectWhenDone: nil`, which disconnects whenever the sync itself opened the link, exactly the case of a Personal Automation with the app in the background. Consequences: (1) the on-demand `CMD_BATTERY` was dead code (`isConnected` was already false), so the shortcut answered with the stale in-memory level or `nil`; (2) the disconnect landed on the sync's last file ACKs, which the band then offered again on the next connection. The sync now keeps the link (`disconnectWhenDone: false`) and the radio is released only at the end of the intent, and only if there was no live link before it.
- **A sync failure was invisible in both state intents** (`Intents/CheckBandBatteryIntent.swift`, `Intents/GetSleepStateIntent.swift`): both swallowed the error with `try?`. `GetSleepStateIntent` answered "asleep/awake (data from X)" without saying that the data from X was all there was, the opposite of the intent's purpose, which is to never let an automation silently act on stale state. The error now goes to the log in both and, in the sleep one, to the dialog ("…, sem sincronizar agora", "…, without syncing now").

- **The iPhone pairing sheet killed the handshake as it appeared** (`BLE/BandManager.swift`): a write rejected with `CBATTError.insufficientAuthentication` (or `.insufficientEncryption` / `.insufficientAuthorization`) is exactly iOS announcing it is about to ask the user to pair, and `didWriteValueFor` called `failAuth` on it. It is the only concrete signal the app has of the second prompt; it now enters the wait with `stage = .phone` instead of tearing down authentication the instant the sheet comes up.
- **An HMAC mismatch on first pairing could still be read as "AuthKey incorreto" (wrong AuthKey)** (`BLE/BandManager.swift`): when the band's `sub=16` came **with** a parseable watch-nonce, the flow diverted to `handlePotentialWatchNonce` without ever entering `.awaitingPairingConfirmation`, and two mismatches later the app dropped the link that was holding the dialog. A band we have never authenticated against (persisted in `everAuthenticated`) has no way of signing a verifiable nonce before the bond exists: that mismatch now starts the pairing wait.
- **A repeated `sub=16` didn't extend the wait** (`BLE/BandManager.swift`): `beginPairingConfirmationWait` returned early on the second call, so the band could repeat the request every ~6 s for three minutes while the 120 s watchdog expired underneath. Each repeat now pushes the deadline out.
- **The retry budget was spent waiting for a human** (`BLE/BandManager.swift`): a slow pairing used up the 4 attempts of `retryAuthAfterReconnect` and ended in `AuthError.badHMAC`, "AuthKey incorreto" (wrong AuthKey), the one diagnosis that sends the user to re-extract a key that was right. Within the pairing window the retry is skipped and the watchdog only re-arms.
- **The auth watchdog cut off the wait for the user** (`BLE/BandManager.swift`): silence during pairing is a person reading a dialog. The watchdog now re-arms while the window is open and fails only when it expires, with `AuthError.pairingNotConfirmed`, which is actionable ("toque em conectar para tentar de novo", "tap connect to try again"), instead of "Tempo esgotado durante autenticação" (timed out during authentication).
- **"Sync timed out." on a link held open for a long time** (`BLE/BackgroundSyncManager.swift`, `BLE/BandSyncer.swift`): the band stopped answering while the status still read "Connected", and only relaunching the app (a fresh connection) cleared it. A file-list timeout on a link that was already up now drops the connection, re-authenticates and retries the sync once; a file that stalls is still just skipped. There is no retry inside a `BGAppRefreshTask`, from the Shortcuts intents, or on a background wake (their time budget can't hold a reconnect, and a coalesced caller of that kind turns it off for the shared sync), nor when the old link doesn't drop. The reconnect waits for a connect already under way instead of starting a second one. Both timeout points log at error level (persisted on the device, with values marked `.public` so they don't read `<private>`), with the step that stalled. Validated on hardware (2026-09-25) after a 30-minute open link; the exact cause of the desync has not yet been seen in the log.
- **The Dashboard's "last sync" time froze** (`UI/Dashboard/DashboardView.swift`): the relative time was computed at render and nothing re-rendered it; a 30 s `TimelineView` keeps it current, and a sync under a minute old reads "Just now".
- **The two Dashboard tiles had different heights** (`UI/Dashboard/DashboardView.swift`, `UI/DesignSystem/MBMetricTile.swift`): the battery tile has no footer unless charging. Both now match the taller one.
- **The AuthKey migration could delete the only copy of the key** (`Auth/AuthKeyStore.swift`): the legacy (bundle-id) item was deleted even when saving under the fixed service failed. It is now deleted only after a successful save; on failure the legacy key is still returned and the migration retries on the next `load`.
- **A watch face or app upload hung forever when the link dropped** (`BLE/BandManager.swift`, `BLE/Upload/DataUploadService.swift`): the pacing continuation was only resumed by `peripheralIsReady`, which never fires on a dead link. `resetState` now resumes it, and the upload fails with `notConnected` ("Band not connected.") instead of finishing into a dead link and showing the face as installed. The check looks at the GATT link, not the auth state, so a band session restart mid-upload doesn't abort it.
- **Frames larger than the MTU silently lost fragments** (`BLE/BandManager.swift`): `writeSPP` sent every fragment at once, and CoreBluetooth drops a write-without-response while its buffer is full, so a large calendar frame (or upload chunk) arrived corrupted. Fragments now go through a queue drained on `peripheralIsReady`, every later write queues behind it so no bytes interleave into the frame, and a small write with a full buffer queues too instead of being dropped.
- **A truncated daily summary became invented data** (`BLE/PacketParser/DailySummaryParser.swift`): the guard required 30 bytes but the parser reads 41, and the buffer still carries the trailing CRC-32; `LEReader` returns 0 past the end, so a short file was written with zeros (or CRC bytes as SpO₂) and ACKed. The guard now accounts for the CRC: it requires the fields through calories, and the SpO₂ block is read only when complete, so a file ending before it keeps its steps and heart rate.
- **An orphaned bond sat in a silent reconnect loop** (`BLE/BandManager.swift`, `BLE/BandAuthenticator.swift`): `CBError.peerRemovedPairingInformation` means the band forgot a bond the iPhone still keeps; no reconnect fixes that. A new `AuthError.staleBond` tells the user to forget the device in Settings › Bluetooth. `CBError.encryptionTimedOut` (iOS sheet dismissed or expired) is now recognised as such, keeping the window open for the next attempt.
- **A sleep test that had never passed** (`My BandTests/SleepReconciliationTests.swift`): its expectation contradicted `sanitizeStages` (an inner REM inside a deep stage is dropped, not carved out). The test now covers the cross-file overlap it was written for.

### Fixed

- **Sync hung until the timeout with the link apparently healthy** (`BLE/BandManager.swift`): the band reopens the session on its own right after the post-auth init (its sequence counter back to 0, a new watch-nonce, a new `sub=27`). The app ignored that `session-config-accept` because it already considered itself `.connected`, and kept using the **old** session keys: the band ACKed the transport frame and silently dropped the command, unable to decrypt it. Result: "Health sync started" followed only by ACKs and "Tempo esgotado durante sincronização" (timed out during sync). GadgetBridge (`XiaomiBleProtocolV2.processPacket`) redoes the handshake on **every** session config packet; the app now does the same when the band reopens the session (limited to 3 restarts per connection), re-deriving the keys. The duplicate guard is now restricted to the in-flight handshake, which is where the 005F bug lived. Confirmed in the hardware log of 2026-09-05.
- **An HMAC mismatch from a nonce race dropped the connection** (`BLE/BandManager.swift`): a watch-nonce the band had already put on the air when our `CMD_NONCE` went out can't verify: it was signed against a phone-nonce the band hasn't seen yet. Up to 2 mismatches per nonce exchange are now tolerated before escalating to a reconnect; a genuinely wrong AuthKey always mismatches and still ends in `AuthError.badHMAC`.
- **First pairing didn't wait for the user's acceptance** (`BLE/BandManager.swift`, `BLE/BandProtocol.swift`, `UI/ConnectionStatus+UI.swift`, `UI/Setup/ConnectingView.swift`): the band announces first pairing with `auth sub=16` and only emits a verifiable watch-nonce after the user accepts **on the band and on the iPhone** (the iOS Bluetooth pairing sheet). The app treated the pre-acceptance nonce as a wrong AuthKey and dropped the link to "retry", which dismisses the very prompt it was waiting for, and the 4 retries burned through in a few seconds, before any chance to tap the screen. `sub=16` now enters an `.awaitingPairingConfirmation` state: the handshake waits (120 s window), a mismatched HMAC during the wait drops nothing, and the screen instructs "Aceite o pareamento na pulseira e confirme no iPhone" (Accept the pairing on the band and confirm on the iPhone). Confirmed in the hardware log of 2026-09-05.
- **A successful handshake dropped by a late nonce** (`BLE/BandManager.swift`): after `CMD_AUTH`, the band re-emits a watch-nonce of its own (a handshake restart on its side). Verifying it against our already-superseded phone-nonce always fails, and the app dropped the link one packet away from success. The same late nonce, when it arrived **after** `sub=27`, was ignored and the connection completed normally: both cases appear in the same log. Nonces received with `CMD_AUTH` in flight are now ignored; the `sub=27` confirmation decides.
- **"Tempo esgotado durante autenticação" (timed out during authentication) lied** (`BLE/BandManager.swift`, `BLE/BandAuthenticator.swift`): `AuthError.timeout` was only thrown from a disconnection, so the message appeared for link drops and there was no real timeout: a band that simply went silent hung forever. Added a real watchdog (20 s, 120 s during pairing), re-armed by every auth packet that makes progress, and a distinct `AuthError.linkDropped` for the link drop.
- **Auth retries in bursts** (`BLE/BandManager.swift`): `retryAuthAfterReconnect` reconnected immediately, spending the 4 attempts in seconds. The teardown is now delayed with a growing delay (1–4 s), an already-scheduled retry isn't rescheduled by a second nonce, and the deliberate teardown no longer shows up as an error in the UI.
- **The AuthKey could vanish between versions and sessions** (`Auth/AuthKeyStore.swift`): the Keychain item was keyed by the bundle id read at runtime, so a bundle/target rename would leave the app "without a key" with the key intact in the Keychain under the old name; it now uses a fixed `service`, with automatic migration of the legacy item on the first read. Also: `save` now updates in place (the previous `delete`+`add` lost the key if the add failed), the item is pinned as non-synchronizable (an iCloud Keychain entry can no longer shadow the local one), and a **locked** Keychain (background relaunch before the first unlock after boot) is no longer read as "no key", which sent an already-paired user back to setup.

- **Duplicated/overlapping sleep between resyncs** (`Health/HealthKitManager.swift`, `BLE/PacketParser/SleepPacketParser.swift`, `BLE/BandSyncer.swift`): resyncing a night still in progress (every BLE wake) reported the same real phase with a later end each time; the old sync-id included the exact end, so HealthKit's dedup never recognised the update and the overlaps piled up (~65 days of duplicated InBed observed in a real export). `writeSleep` now groups sessions whose windows overlap, re-sanitizes the pooled set, and uses stable ids (phase start + type, without the end). A one-time historical repair migration (`repairSleepHistoryOnce`) rebuilds Health from the local SwiftData on the next sync.
- **Auth stuck in an infinite loop on first connection** (`BLE/BandManager.swift`): the notify subscription on 005F (added as a diagnostic) made the app process the session accept twice, each time restarting the nonce exchange with a new nonce. The band never answered either one and dropped the connection; since the automatic reconnector never gives up, the app kept trying forever without ever authenticating. Confirmed on hardware (2026-09-05). 005F has no RX role in the protocol: it is no longer subscribed for notify, and `handleSessionConfigResponse` gained an idempotency guard against any future duplicate delivery. (That guard was too broad and was restricted to the in-flight handshake; see the "Sync hung until the timeout" entry above.)

### Changed

- **Configuration pushes only when they change** (`BLE/CalendarSyncService.swift`, `BLE/WeatherSyncService.swift`): language, calendar and reminders were re-sent to the band on **every** sync (minutes apart), even with no change: wasted radio and, for reminders, needless delete+recreate churn. Each section now keeps a stable signature (CRC-32 of the content, persisted in `UserDefaults`; Swift's `Hashable` is salted per process and can't be persisted) of the last payload sent and **skips** when nothing changed: language compares the locale code; calendar compares the events' title/start/end/all-day/alarm; reminders compare title/due date and, if equal, avoid the whole delete+recreate (the ids assigned by the band stay valid). **Weather** gained a throttle: the proactive push at the end of the sync only re-fetches/re-sends every 30 min, but the reply to the **band's request** (`onWeatherConditionsRequest`, which the weather screen waits for) **always** goes through, with no throttle.
- **Weather follows the iPhone's real location (GPS), no longer a fixed Guarapuava** (`BLE/WeatherSyncService.swift`, `Info.plist`): the band asked for weather and always got Guarapuava's (fixed coordinates, with the requested name merely echoed). Now **every** band weather request is answered with the weather at the **iPhone's current location** via `CLLocationManager`: if you are in Cabral, in Curitiba, the band shows Curitiba's weather. Resolution is layered: (1) **iPhone GPS** (a single fix reused for 5 min across consecutive requests, with an 8 s timeout and fallback to the last cached fix; place name by reverse geocoding, cached per ~1 km cell); (2) if location is **denied/unavailable**, it falls back to the **named** location the band asked for, geocoded; (3) finally, to the default (Guarapuava). The key the band asked for is echoed so it can bind the reply to the tile that is waiting. Reuses the location permission and the `location` background mode already present (used by workout GPS); the `NSLocationWhenInUseUsageDescription` text now also mentions weather.
  - **Name geocoding (fallback) with neighbourhood care:** when GPS is unavailable and it falls back to the named location, the band's locations tend to be *neighbourhoods* of the home city (e.g. "Santa Cruz" is a neighbourhood of Guarapuava), and geocoding the raw name would land on a distant city of the same name, so it tries the name **qualified with the home city** and only accepts it if it lands in the **Guarapuava area** (< 60 km), otherwise the raw name (a genuinely different city). The result is cached/persisted (the band repeats the request on every connection and Apple's geocoding is rate-limited).
- **Sync setup slimmed down and with more chances in the background** (`BLE/BackgroundSyncManager.swift`, `BLE/BandSyncer.swift`, `UI/Dashboard/DashboardView.swift`, `Info.plist`):

### Changed

- **Workout end fetches the files the band names instead of relisting the backlog** (`BLE/BandManager.swift`, `BLE/WorkoutGpsService.swift`, `BLE/BandSyncer.swift`): `workoutStatusWatch` (status=finished) carries the `activityFileIds` of the just-recorded workout, which used to be discarded: the app only read the `status` and fired a full `syncToHealth()` (FETCH_TODAY + FETCH_PAST). Now `BandManager` passes the ids in the `onWorkoutStatusWatch(status, fileIds)` callback; `WorkoutGpsService.onWorkoutFinished(fileIds)` hands them to `BandSyncer`, which calls the new `syncWorkoutFiles(_:)`: it fetches, parses, writes to Apple Health and ACKs **exactly** the workout's files (summary + GPS route), skipping the listing. ### Fixed

- **Overlapping and multiplied sleep stages (`BLE/PacketParser/SleepPacketParser.swift`)**: the Mi Band 10 transmits multiple type 17 packets (sleep stages) cumulatively during the same night; the parser blindly accumulated every packet, producing nights with 60 h to 400 h of sleep written to Apple Health. Added the `sanitizeStages(_:)` function, which sorts and merges the timeline, removing overlaps.
- **Negative timestamps and 1928/1970 dates in sleep/sensors (`BLE/PacketParser/SleepPacketParser.swift`)**: `readSamples` used `r.i32()` for `firstRecordTime`, turning values with bit 31 set into negative integers (year 1928), and also interpreted start-of-day offsets as unix epoch (year 1970). Updated to `r.u32()` with alignment to the session's day and a strict `sampleTime > 1_500_000_000` guard.
- **Impossible SpO₂ values (251%) and old dates in the daily summary (`Health/HealthKitManager.swift`, `BLE/PacketParser/DailySummaryParser.swift`)**: `writeDailySummary` wrote daily extremes without sanitizing, letting through the band's placeholder/sentinel bytes (such as `0xFB` = 251%) and leftover timestamps (such as year 2010). Added physiological range validation (`35...220` for HR, `50...100` for SpO₂) and contemporary date validation (`validDateRange`).
- **Astronomical steps in Apple Health (millions in a day) from a swapped activity file** (`BLE/BandSyncer.swift`, `BLE/PacketParser/DailyActivityParser.swift`): after days without syncing (expired app), the sync inserted absurd step totals (e.g. 1,466,779 in a day), attributed to My Band itself. Root cause, confirmed by the console of the real run: activity chunks arrive on characteristic `0053` **with no file id**, so `fetchActivityFile` correlated response↔request **by time only**, through a single callback. With the backlog piled up, while the band was still dumping a large file (a night of sleep, 47,987 bytes) the app had already requested the next one; the sleep stream fell into the **daily-details** receiver and **passed the CRC** (it was an intact file, just the wrong one). Parsed under the daily-details meta, `DailyDetailsParser` walked sleep bytes as minute records up to the 2000-iteration ceiling, reading the 14-bit steps field over unrelated data (it saturates near 16,383/min): ~1.4M phantom steps. Fixes:
  - **Id check on fetch (root cause):** every activity file repeats its own 7-byte id at the start of the payload; `fetchActivityFile` now rejects (`SyncError.fileIdMismatch`) any file whose embedded id ≠ the requested one, without ACKing: the band offers it again on the next sync. (Aligns with the file↔request matching of GadgetBridge's `XiaomiActivityFileFetcher`.)
  - **Robust reassembly:** `ActivityFileReceiver` now ignores tail chunks from an earlier transfer that arrive **before** the first chunk (`current==1`) of the current file, which used to corrupt the buffer and shift every record.
  - **Parser sanity (defence in depth):** `DailyDetailsParser` discards the whole file if any minute reports physically impossible steps (>1000/min ≈ 17 steps/s), a sign of misalignment, so no absurd value reaches Apple Health even if something slips past the id check.
- **The connection to the band didn't recover after time in the background** (`BLE/BandManager.swift`, `BLE/BackgroundSyncManager.swift`, `AppServices.swift`, `My_BandApp.swift`, `UI/Dashboard/DashboardView.swift`): on returning to the foreground after a while, the app stayed "disconnected" with no way to reconnect, and background communication died after the first sync. Causes and fixes:
  - **A "clean" drop didn't re-arm the connection.** `didDisconnectPeripheral` only reconnected when there was an `error`; a drop without an error (app suspended, out of range) fell into `.disconnected` and stayed dead. Now **any** disconnection not initiated by the user re-arms a *standing connect* (`armStandingReconnect`): a `central.connect` with no timeout that iOS keeps pending and re-establishes (waking the app via state restoration) as soon as the band comes back in range, **with no attempt limit**. Introduced the `autoReconnect` flag, turned on when connecting and off only on "Forget band"; `disconnect(userInitiated:)` distinguishes the user's forget from the background teardown.
  - **The background sync killed the standing connect.** The post-sync teardown (and the one on BGTask expiry) called `disconnect()`, cancelling the connection intent: without it CoreBluetooth had no reason to reconnect or wake the app, so background stopped after one sync. These paths now use `disconnect(userInitiated: false)` (releases the active link but keeps auto-reconnect), and the BLE-wake sync keeps the link (`disconnectWhenDone: false`) for constant communication (push events: find phone, workout, weather).
  - **Connection backoff gave up for good.** On exhausting the 5 attempts, `scheduleReconnect` went to `.disconnected` and stopped. It now falls back to a standing connect, which never gives up.
  - **No reconnection on returning to the foreground.** Added a trigger on `scenePhase == .active` (`AppServices.reconnectIfNeeded`) that resumes the connection if there is a paired band and the link is down: an extra guarantee against a dead "disconnected".
  - **The Dashboard didn't offer to reconnect.** When connected, the screen only had "Sync" (disabled when disconnected) and "Forget"; now there is a **Reconnect** button when the link is down (shows "Connecting…" during the attempt).
- **Steps/distance overestimated after two syncs in a row** (`Health/HealthKitManager.swift`): reconciliation (`writeReconciledActivity`) wrote the band's surplus over the iPhone with a **constant** `HKMetadataKeySyncVersion` (1). HealthKit only replaces a sample with the same `HKMetadataKeySyncIdentifier` when the new version is **strictly greater** (an equal or lower version → the save is ignored), so the first surplus written for a minute stayed frozen and no re-sync could correct it. Combined with the iPhone pedometer's latency (it often hasn't yet written the recent minutes when the app reconciles them), the delta came out inflated (`band − ~0`) and stuck, doubling the count for those minutes; a second sync, which should have corrected it, was discarded by the version rule. Two-part fix: (1) a **monotonic sync version** (seconds since the epoch) on reconciled samples, so a later sync with the correct (usually smaller) delta actually **replaces** the earlier one, healing already-inflated data; (2) a **settle window** (`reconcileSettleWindow`, 15 min) that skips recent minutes until the iPhone has finalized them: they are reconciled on a later sync (the band re-offers today's file while it grows, so nothing is lost). Raw HR/SpO₂ keep their per-minute granularity intact (no iPhone equivalent, no double count) and the immutable types (sleep/manual/workout) keep the constant version.
- **The app lost the connection/sync with the band in the background** (`AppServices.swift` (new), `My_BandApp.swift`, `AppDelegate.swift`): creating the `BandManager` (and the `CBCentralManager` with a restore identifier) and **all** the dependency wiring lived in SwiftUI's `.onAppear`, which **doesn't run** on a headless relaunch. When CoreBluetooth state restoration relaunched the app because the band came back in range (or on a BGTask), there was no visible scene: `BackgroundSyncManager.configure()` was never called (nil deps → `awaitDependencies()` blew up and threw), `BandSyncer.onAuthenticated` was never wired (the BLE wake didn't trigger a sync) and instantiating the `CBCentralManager` depended on the lazy creation of the App's `@State`, making delivery of `willRestoreState` fragile. In practice background sync only worked if the app had already been opened in the foreground in that process lifecycle. Now an `AppServices.shared` (`@MainActor`) owns the managers and wires them from the **launch path** (`AppDelegate.didFinishLaunching` on iOS, ensuring the `CBCentralManager` is created in time for `willRestoreState`, and the App's `init()` on platforms without UIKit), triggers reconnection to the known device and is idempotent. SwiftUI now only **reads** these managers via `.environment`, with no bootstrap `.onAppear`.
- **GPS was turned on for workouts that don't use GPS (e.g. strength training)** (`BLE/WorkoutGpsService.swift`, `BLE/PacketParser/WorkoutSummaryParser.swift`): on receiving `workoutOpenWatch`, the service started CoreLocation and answered "GPS ready" for **any** sport. Now the sport code is mapped to `WorkoutKind` (an already-validated mapping) and, for indoor/stationary sports (strength, yoga, pool, treadmill, elliptical, rowing machine, jump rope, HIIT, indoor bike, free training), the app answers "GPS disabled" (`{3,2,10}`) and does **not** turn on CoreLocation: the band starts the workout right away, without waiting for/recording a useless fix and without the active location indicator. Outdoor sports (running, walking, hiking, outdoor cycling, open water) keep GPS; an unknown code also keeps GPS (so an unmapped outdoor sport isn't broken). New `WorkoutKind.usesGps` property.
- **Workouts (and measurements/daily detail) reappeared as "not synced" on the band** (`BLE/BandSyncer.swift`): each category's `CMD_ACTIVITY_FETCH_ACK` was conditional on the *write batch* not being empty (`if !workoutsToWrite.isEmpty { … workoutIds.forEach { sendAck } }`). Since `workoutIds` gathers the fetched **summary and GPS route** files, it was enough for the summary to have been ACKed on an earlier run (leaving only the GPS), or for a summary to fail to parse, for `workoutsToWrite` to be empty, the `forEach` to be skipped and the file to **never be confirmed**: the band re-offered it indefinitely and marked it as not synced, even though it was already written to Apple Health. The same pattern affected manual measurements and daily detail. Now every successfully fetched file is ACKed **after** its write (a write that throws skips the ACK → re-offer on the next connection, no loss), regardless of whether it produced writable samples.
- **In-workout detail (type=sports, detail=details) was downloaded forever without an ACK** (`BLE/BandSyncer.swift`): `processActivityFiles` routed files by the `XiaomiActivityFileMeta` predicates, but sports files with `detail=details` (the per-second series the band records during a workout: subtype 8 ≈ HR, subtype 22 a larger stream; one of them was 12 KB) matched **no** branch (`isWorkoutSummary` requires `.summary`, `isWorkoutGps` requires `.gps`, the activity branches require `type=.activity`). They were fetched but never ACKed, so the band re-offered them on every connection: a perpetual re-download. Now these files route to the new `WorkoutDetailsParser` (see _Added_: per-second HR series) and are ACKed together with the workout's summary/route; and the final `else` ACKs any file that still matches **no** parser, mirroring GadgetBridge (`XiaomiActivityFileFetcher` ACKs every file **before** creating the parser, discarding what has no parser). The ACK is safe: routing is only reached after `fetchActivityFile` returns without throwing, preserving the "ACK only after a successful fetch" invariant. Validated by `ActivityFileRoutingTests` with the real captured file-ids (Mi Band 10, 2026-06-23) and live on hardware.
- **Distinct sleep sessions were discarded (weak dedup hash)** (`BLE/PacketParser/SleepPacketParser.swift`): `rawDataHash` used an XOR fold (`$0 ^= Int($1)`), whose result collapses into 0–255. Since `BandSyncer.persistIfNew` dedups sleep sessions by that hash, different nights collided and the second was silently ignored in SwiftData (Apple Health was not affected: it always rewrites). Replaced with 64-bit FNV-1a over the whole file.
- **Workout distance/energy counted twice with the daily detail** (`Health/HealthKitManager.swift`, `BLE/BandSyncer.swift`): a workout writes `distanceWalkingRunning`/`activeEnergyBurned` via `HKWorkoutBuilder`, which Apple Health also adds to the daily totals; at the same time the daily-detail file covers the same minutes. Both samples come from the app → workout distance/energy went in twice. Now `writeReconciledActivity(_:excludingWorkouts:)` skips minutes inside a workout window for distance and energy (steps aren't written by the workout, so they stay reconciled). To know the windows, the daily detail is now processed in a batch (after the workouts) in `processActivityFiles`, with the ACK only after the writes.
- **The authentication error state was lost on disconnection** (`BLE/BandManager.swift`): `didDisconnectPeripheral` overwrote the state with `.disconnected` right after `resetState()` had set `.error(...)`, hiding the failure from the UI. It now forces `.disconnected` only when it won't reconnect.
- **Auth/upload continuations could leak** (`BLE/BandManager.swift`, `BLE/Upload/DataUploadService.swift`): if a new attempt started with an earlier continuation still pending (e.g. characteristics rediscovered on a reconnect in the middle of auth), the old one was never resumed and hung until the timeout. The earlier one is now resumed with an error before being replaced.

- **Steps/distance/energy counted twice in Apple Health** (`Health/HealthKitManager.swift`, `BLE/BandSyncer.swift`): the iPhone (motion coprocessor) and the band record the same quantities, and Apple Health **adds** every third-party source on top of the iPhone instead of merging (the private iPhone+Watch dedup doesn't apply to third parties and there is no API to change the aggregation): a 200-step walk showed up as 400. The app wrote the daily step/energy total (`writeDailySummary`) and per-minute distance (`writeMinuteSamples`) raw, adding to the iPhone. Now these three quantities go through **reconciliation on write** (`writeReconciledActivity`): for each minute, only the band's **surplus** over what the iPhone already recorded in that minute is written (`delta = max(0, band − iPhone)`, via `HKStatisticsCollectionQuery` in 1-min buckets, source ≠ this app), so the per-minute total becomes `max(band, iPhone)`. Result: no more double count, **the iPhone's Mobility metrics preserved** (Asymmetry/Step Length/etc., which the band doesn't produce and which depend on Fitness Tracking being on) and steps without the phone still captured. HR and SpO₂ stay raw in `writeMinuteSamples`: no iPhone equivalent, per-minute granularity intact; `writeDailySummary` keeps only HR/SpO₂ extremes and resting HR. Reconciliation depends on the daily-detail (per-minute) file; if the user denies the read in HealthKit, the iPhone sums come back empty and the band's full value is written (the safe direction, band as source).
- **Sparse GPS route during the workout** (`BLE/WorkoutGpsService.swift`): CoreLocation's `distanceFilter` was 5 m, so a new point was only delivered (and streamed to the band) every 5 m travelled: a cadence tied to pace (~1.5 s running, ~3.6 s walking) and **no points** when stopped or very slow. Switched to `kCLDistanceFilterNone`, delivering every fix CoreLocation computes (~1 Hz, uniform in time) for a smoother route.
- **The workout GPS route wasn't exported (and could abort the sync)** (`Health/HealthKitManager.swift`): `writeWorkouts` built each route `CLLocation` with `horizontalAccuracy: hdop ?? -1`. CoreLocation treats negative accuracy as an **invalid** sample, and `HKWorkoutRouteBuilder.insertRouteData` rejects the whole batch if any is invalid, so V1 tracks (no hdop) made the write throw, propagating out of `syncToHealth()` **after** the workout was already written and before the ACK. Also, hdop (dimensionless) was used directly as metres. Now hdop is converted to an estimate in metres (×5 m UERE; a conservative fixed value when absent/zero), fixes are sorted and deduplicated into strictly increasing timestamps (a builder requirement), and attaching the route is isolated in `do/catch`: a route failure is only logged, without taking down the batch or the ACK. The route now also carries `speed`/`course` when available.
- **The route could fail to match the workout over a timestamp difference** (`Health/HealthKitManager.swift`): the summary and GPS files get the same start timestamp, but the two file-ids can differ by 1–2 s; exact-key matching discarded the route in that case. Now, with no exact match, the closest track within 120 s is chosen.
- **GPS kept being streamed with the workout paused** (`BLE/WorkoutGpsService.swift`): `workoutStatusWatch` status=2 (paused) wasn't handled, so the app kept sending `workoutLocation` during the pause, possibly inflating distance/route on the band. Now pausing stops sending positions (keeping CoreLocation active for instant resume) and resuming (status=1) streams again. Also fixed the header comment that listed the wrong status codes (the correct ones, confirmed in the proto, are `0=started, 1=resumed, 2=paused, 3=finished`).
- **The weather forecast didn't show on the band** (`BLE/WeatherSyncService.swift`, `BandManager.swift`): the Mi Band 10 pulls weather by request/response (it sends `CMD_REQUEST_CONDITIONS_FOR_LOCATION` (type=10, subtype=3) on connect and when the weather screen opens), but the app only pushed proactively at the end of `syncToHealth()` and **discarded** the band's request (it fell into the `default` of `handleProtoCommand`). The band's weather screen waits for the reply to that request, so the standalone push didn't populate it. Now `BandManager` routes type=10 (`handleWeatherCommand`): subtype=3 fires the new `onWeatherConditionsRequest` callback, and `WeatherSyncService` answers with a weather push. The reply echoes the location key/name the band asked for (`requestedKey`/`requestedName`) so it binds the data to the right location; status≠0 in the band's replies to our pushes is now logged. Confirmed against GadgetBridge's `XiaomiWeatherService` (`onConditionRequestReceived`).
- **The daily forecast covered one day too few** (`BLE/WeatherSyncService.swift`): we sent 6 entries (today..+5); GadgetBridge covers today + 6 days = 7 entries (today..+6). Open-Meteo's `forecast_days` went to 7 and the loop sends up to 7 entries.
- **Sleep data lost to a premature ACK** (`BLE/BandSyncer.swift`): `CMD_ACTIVITY_FETCH_ACK` was sent inside the per-file loop, **before** the batch write to HealthKit (sleep/manual/workout are accumulated and written after the loop). If the write failed or the app was killed between the ACK and the write, the band marked the file as synced and didn't re-offer it: permanent loss. Each category's ACK is now sent only after the corresponding write is confirmed (daily summary/detail ACKed inline; sleep/manual/workout after the batch `write...`). The SPP transport ACK (type=1, per frame) is independent and was not affected.
- **The language sent to the band came out as `en_br`** (`BLE/CalendarSyncService.swift`): `Locale.current.language.languageCode` reflects the app's **resolved** locale, which falls back to English when the bundle has no Portuguese localization, even with the device in pt-BR. Switched to `Locale.preferredLanguages.first`, which returns the user's actual choice (`pt_br`).
- **Crash on HealthKit authorization** (`NSInvalidArgumentException: Authorization to share the following types is disallowed: HKCategoryTypeIdentifierAppleStandHour`): `.appleStandHour` is a reserved type, computed by the system (Apple Watch), and can't be in a third-party app's `requestAuthorization(toShare:)`. Removed from the type set and from the write in `writeDailySummary`. The band's stand-hours mask stays local only (there is no "stand hour" type writable by third parties in HealthKit).

### Added

- **Direct reconnection by identifier (`BandManager.reconnectToKnownDevice`)**: on relaunch, instead of scanning from scratch, the app retrieves the known peripheral via `retrievePeripherals(withIdentifiers:)` and issues a `connect()` with no timeout (iOS reconnects on its own as soon as the band comes in range). `RootView` uses a `@Query` of `BandDevice` to get the identifier deterministically at bootstrap, falling back to a scan when there is no known peripheral. ### Changed

- **Sync fetches the full history, not just the current day (`BandSyncer.fetchFileIds`)**: the flow now chains `CMD_ACTIVITY_FETCH_TODAY` → `CMD_ACTIVITY_FETCH_PAST` (subtype 2) and merges the two file-ID lists, mirroring GadgetBridge's `XiaomiHealthService.handleActivityFetchResponse`. Before, only `FETCH_TODAY` was sent, so earlier nights ("past" records) were never offered by the band. `FETCH_PAST` is best-effort (an empty reply or a timeout doesn't abort the sync). New builders `XiaomiProto.fetchTodayCommand`/`fetchPastCommand`.
- **HealthKit writes decoupled from SwiftData dedup (`BandSyncer.syncToHealth`)**: sleep sessions are now always (re)written to Apple Health; dedup by `HKMetadataKeySyncIdentifier` makes the operation idempotent, so data deleted by hand from the Health app shows up again on resync. `persistIfNew` still prevents duplicate local records in SwiftData.

### Fixed

- **The activity file ACK used the wrong proto field (`BandSyncer.sendAck`)**: `CMD_ACTIVITY_FETCH_ACK` wrote the file ID into `activityRequestFileIds` instead of the dedicated `activitySyncAckFileIds` field (GadgetBridge `ackRecordedData`). Since the ack field was empty, the band didn't mark the file as synced: it could re-offer it or keep it in storage. New builder `XiaomiProto.ackCommand`.
- **Sleep stages didn't appear in Apple Health (`BLE/PacketParser/SleepPacketParser.swift`)**: the parser had three protocol bugs that prevented extracting the stage packets. (1) The stage packet magic is read **little-endian** by GadgetBridge (bytes `FB FA FC FF`), but the parser looked for `FF FC FA FB`, so it never found the stages. (2) The packet's `ts` timestamp is **little-endian**, but was read as big-endian. (3) Bits[11:0] of each type 17 entry are the **duration** of that stage (accumulated from the cursor), not an absolute offset: the previous duration calculation (`next − current`) produced truncated/invalid phases. Rewritten as a faithful port of `SleepDetailsParser.java` (versioned header via `validData`, cumulative cursor). The `awake`/`core`/`deep`/`rem` stages now populate Apple Health.
- **Heart rate during sleep missing from Apple Health's "Comparisons" tab**: the sleep parser discarded the HR/SpO₂ section embedded in the sleep file (`u8` samples with `unit`/`count`/`firstRecordTime`). These samples are now extracted (`ParsedSleep.heartRates`/`spo2`) and written to HealthKit within the sleep window via `BandSyncer.syncToHealth`, letting Apple Health correlate HR/SpO₂ with sleep. `writeSleep` now also writes an enclosing `inBed` sample for "time in bed".
- **Reassembly of fragmented BLE frames (large activity files)**: `005E` is a *byte stream*: an SPP V2 frame can exceed the MTU and arrive split across several notifications (e.g. a 912 B daily details file arriving as 495 + 417). The code treated 1 notification = 1 frame, rejected both halves as "Malformed", never ACKed the `seq`, and the band retransmitted every ~6 s indefinitely: the daily details was never assembled (timeout). Added an RX buffer in `BandManager.drainFrames()` that accumulates bytes and extracts complete frames by `payloadLen` (with resync to the `A5 A5` preamble), mirroring `XiaomiSppProtocolV2.processPacket`. `ActivityFileReceiver` now completes at `num == total` (GadgetBridge semantics).
- **`writeSPP` ignores writes to a peripheral outside the `.connected` state**: avoids `API MISUSE: can only accept commands while in the connected state` when an ACK is queued right after the auth-retry disconnect.
- **Re-authentication loop every ~6 s: DATA frames weren't ACKed**: SPP V2 is a reliable windowed transport (TX_WIN/seqNum). Every DATA frame received from the band must be confirmed with an `AckPacket` carrying the same `seqNum` (GadgetBridge `XiaomiSppProtocolV2.processPacket` → `sendAck`). The app processed the packets but never sent an ACK, so the band assumed loss and retransmitted the whole handshake (sub=26/sub=27) indefinitely, even after auth and sending the init. Added `BandManager.sendAck(seqNum:)`, called for every DATA frame received.
- **First pairing: the band's HMAC failed and got stuck in `.error`**: on first pairing the band sends `sub=16` and the first watch nonce produces an HMAC that doesn't match; only a clean reconnection yields a verifiable handshake. Before, the app went to a permanent `.error` (it only recovered if the band itself dropped the link). Now `retryAuthAfterReconnect()` drops and reconnects automatically (up to `maxAuthRetries=4`) on detecting an invalid HMAC, replicating the path that provably authenticates. `didDisconnectPeripheral` honours the `retryAuthOnDisconnect` flag to reconnect even on a "clean" disconnection.
- **Authentication diagnostic logs**: hex dump of every auth channel packet by subtype, nonces (phone/watch) and band-vs-app HMAC comparison, and an attempt to extract a watch nonce from `sub=16` packets. Nonces/HMACs are logged (they aren't secrets); the AuthKey and session keys are never logged.
- **Post-authentication: the band re-triggered auth every ~6 s ("Duplicate auth response" loop)**: after a successful `CMD_AUTH`, the app only sent `setCurrentTime`. GadgetBridge (`XiaomiSupport.onAuthSuccess`) sends `setCurrentTime` **+** `SystemService.initialize()`, starting with `CMD_DEVICE_INFO` (type=2, sub=2), `CMD_DEVICE_STATE_GET` (sub=78) and `CMD_BATTERY` (sub=1). Without that initialization handshake the band considers the session incomplete and resends the auth confirmation indefinitely. Added `BandManager.sendPostAuthInit()` and `XiaomiProto.systemCommand(subtype:)` + the `XiaomiSystemCmd` enum.
- **`BandManager.centralManager(_:didDiscover:)`: auto-connect blocked by state restoration**: when `willRestoreState` populated `self.peripheral` before the scan started, the `if self.peripheral == nil` guard prevented `connect(to:)` from being called on rediscovering the band. The log stopped at "Discovered: Xiaomi Smart Band 10 …" with no connection attempt. Fixed: it now connects if `self.peripheral == nil` OR if the discovered peripheral has the same `identifier` as the already-known peripheral.

- **`authDeviceInfo`: device_type corrected to iOS (1)**: the `unknown1` field was `0` (ANDROID). Confirmed via analysis of AstroBox-NG (`DeviceType::Ios = 1` for BLE connections on iOS). Changed to `1`.
- **`authDeviceInfo`: app_capability corrected to `0xFFFF_FFFF`**: the `unknown3` field was `224`. AstroBox sends `0xFFFFFFFF` (all bits = all capabilities enabled).

### Fixed

- Manual `Info.plist` created at `$(SRCROOT)/Info.plist` (outside the synchronized folder). `GENERATE_INFOPLIST_FILE = NO` in the pbxproj. Fixes a crash on a physical device: `INFOPLIST_KEY_UIBackgroundModes` produced a `<string>` in the generated plist, but `CBCentralManager` requires `UIBackgroundModes` as an `<array>`: the runtime rejected state restoration with `NSInternalInconsistencyException`.
- `BandManager.init`: `CBCentralManagerOptionRestoreIdentifierKey` now conditioned on `#if !targetEnvironment(simulator)` (the simulator doesn't support CoreBluetooth state restoration).
- `My_BandApp`: `sharedModelContainer` changed from `var` to `static let`. SwiftUI App structs can be recreated during scene setup; a `var` recreated the `ModelContainer` (and the SQLite store) each time, causing a double init visible in the console as pairs of CoreData messages.
- `BandManager.startScan()`: race condition with `CBCentralManager` initialization. Calling `startScan()` from `.onAppear` before `centralManagerDidUpdateState(.poweredOn)` made the guard fail silently and the scan never start. Added a `pendingScan` flag; `centralManagerDidUpdateState` consumes the flag and starts the scan when BT is ready.
- `My_BandApp.sharedModelContainer`: automatic recovery from a corrupted store. Watchdog kills during a write leave the SQLite file in an invalid state. If `ModelContainer` fails on the first attempt, the corrupted store is deleted and recreated before calling `fatalError`.

### Changed

#### BLE protocol: full rewrite based on GadgetBridge (direct source analysis)

Every file in the BLE layer was rewritten based on a full analysis of the GadgetBridge repository
(`XiaomiSppPacketV2`, `XiaomiAuthService`, `MiBand10Coordinator`, `XiaomiHealthService`,
`XiaomiActivityFileFetcher`, `SleepDetailsParser`). The previous implementation was based on the
Mi Band 5/6 protocol (AES-128-ECB + FEE0/FEE1 UUIDs) and didn't work with the Mi Band 10.

- **`MiBandUUID`**: UUIDs corrected for the confirmed V2 protocol: `0051` (cmd notify), `0052` (cmd write), `0053` (activity notify). Standard GATT Heart Rate service removed (that isn't how the Mi Band 10 reports HR). Legacy `005E`/`005F` UUIDs eliminated.

- **`BandProtocol` / `XiaomiSppPacket`**: rewritten as `XiaomiSppPacketV2`:
  - Header reduced from 10 to **8 bytes**: `[0xA5][0xA5][type][seqNum][lenLo][lenHi][crcLo][crcHi]`
  - CRC-16/ARC computed **over the payload only** (not the whole frame)
  - GadgetBridge's exact CRC algorithm: bit-by-bit processing with a 32-bit intermediate and bit reversal
  - Packet types corrected: `ACK=1`, `SESSION_CONFIG=2`, `DATA=3` (they were 0/1/2)
  - Internal structure of the DATA packet: `[rawChannel & 0xf][opCode][data]`; the channel was wrongly in the outer header
  - Session config: fixed binary payload (not protobuf), type `SESSION_CONFIG`, with an `OPCODE_START_SESSION_RESPONSE=2` reply before auth starts

- **`BandAuthenticator`**: rewritten for the HMAC-SHA256 V2 protocol:
  - `CMD_NONCE` (type=1, sub=26): the phone nonce as `Command { auth { phoneNonce { nonce } } }` (nested proto)
  - Parsing the band's reply: `Command.auth(3).watchNonce(31).nonce(1)` and `.hmac(2)`
  - HMAC verification using the derived `decryptionKey` (not the raw `secretKey`)
  - `CMD_AUTH` (type=1, sub=27): `AuthStep3 { encryptedNonces, encryptedDeviceInfo }`; `encryptedNonces` is HMAC-SHA256(encKey, phoneNonce||watchNonce); `encryptedDeviceInfo` is AES-128-CCM(AuthDeviceInfo proto)

- **`XiaomiCrypto`**: PRK derivation corrected:
  - **Before (wrong):** `HMAC-SHA256(key=secretKey, data=phoneNonce||watchNonce)`
  - **After (correct):** `HMAC-SHA256(key=phoneNonce||watchNonce, data=secretKey)`: key/data swapped vs RFC 5869
  - Added a manual AES-128-CCM implementation via AES-ECB (CommonCrypto doesn't expose CCM): CBC-MAC over B₀ + plaintext in 16-byte blocks, followed by encrypt-then-tag with counter blocks; 4-byte tag, 12-byte nonce, no AAD

- **`XiaomiProto`**: added auth command builders with correct nested proto:
  - `phoneNonceCommand`: `Command { auth { phoneNonce(field 30) { nonce(1) } } }`
  - `authStep3Command`: `Command { auth { authStep3(field 32) { encryptedNonces(1), encryptedDeviceInfo(2) } } }`
  - `healthCommand`: `Command { type=8, subtype, health(field 10) { activityRequestFileIds(field 7) } }`
  - Removed a duplicate `import Foundation` and a dead `Locale` extension at the end of the file

- **`BandManager`**: state machine updated for the V2 flow:
  - Correct characteristics: `0051` (notify), `0052` (write), `0053` (activity notify)
  - New `sessionConfig` state: sends the binary config, waits for `OPCODE_START_SESSION_RESPONSE` before starting the nonce
  - DATA packet routing via the inner payload's `rawChannel` + `opCode`
  - AES-CTR decryption with `decryptionKey` for `opCode=ENCRYPTED` packets
  - Callbacks added: `onProtoCommandReceived` (post-auth proto replies on 0051) and `onActivityChunkReceived` (activity chunks on 0053)
  - `handleProtoCommand`: non-auth replies forwarded via `onProtoCommandReceived`

- **`BandSyncer`**: activity sync flow rewritten:
  - Chunk receiver (`ActivityFileReceiver`): format `[totalChunks:2LE][currentChunk:2LE][data...]`, CRC-32 in the last 4 bytes of the reassembled file
  - Correct flow: `subtype=1` (fetchToday) → file IDs as proto in `onProtoCommandReceived` → `subtype=3` (fetchRequest, per file) → chunks in `onActivityChunkReceived` → `subtype=5` (fetchAck)
  - `fetchFileIds` fixed to use `onProtoCommandReceived` (IDs arrive as a proto Command on 0051, not as activity chunks on 0053)
  - `XiaomiActivityFileId`: a helper that identifies sleep files by flags (`subtype==0x03||0x08`)

- **`SleepDetailsParser`** (formerly `SleepPacketParser`): rewritten for the real activity file format:
  - Reads `bedTime`/`wakeupTime` from the fixed header (offsets 10/14, UInt32 LE)
  - Scans the file for the magic `0xFFFC FAFB`, parses the 17-byte header of the stage packets
  - Type `0x11`: UInt16 BE entries where `bits[15:12]=stage`, `bits[11:0]=offset_minutes`
  - Type `0x10`: summary with durations (deep/light/rem/wake) in minutes, used as a fallback

### Added

- `BLE/Crypto/XiaomiCrypto.swift`: cryptographic primitives with no external dependencies (CommonCrypto only): HMAC-SHA256, HKDF-expand (RFC 5869 §2.3), AES-ECB (single block), manual AES-CTR with IV=key (V2 quirk: "I wish I was kidding"), manual AES-128-CCM with CBC-MAC + encrypt-then-tag, `SessionKeys` derivation.
- `BLE/Protocol/XiaomiProto.swift`: minimal in-house protobuf encoder/decoder: varint encode/decode, uint32/string/bytes/message fields, builders for auth and health commands, a field reader for parsing the band's replies.
